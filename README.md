# LLM Console

Консольное Go-приложение для диалога с LLM. Переписка сохраняется в JSON
и автоматически подгружается при следующем запуске.
Оно настроено на DeepSeek и использует его OpenAI-совместимый endpoint
`POST /chat/completions`.

## Запуск

1. Создайте файл конфигурации и внесите ключ. Он исключён из Git:

   ```bash
   cp config.example.json config.json
   ```

   В `config.json` укажите `api_key`. Остальные поля уже настроены на DeepSeek.

2. Запустите чат:

   ```bash
   go run ./cmd/llm-console
   ```

   После запуска открывается диалог:
   Enter отправляет сообщение, после ответа можно сразу задать следующий вопрос.
   В контекст попадают саммари и сообщения, ещё не вошедшие в него,
   а также рабочая и долговременная память.
   Полная переписка сохраняется и отображается при запуске.

   Команды чата:

   - `/exit` или `/quit` — выход (также Ctrl+D на пустой строке);
   - `/clear` — удалить диалог и саммари, сбросить расход токенов; рабочая и долговременная память сохраняются;
   - `/memory` — просмотр и ручное редактирование памяти;
   - `/agent` — показать текущего агента; `/agent <директория>` — переключить;
   - `/profile` — показать единственный статичный профиль агента;
   - `/multi` — начать многострочное сообщение;
   - `/send` на отдельной строке — отправить многострочное сообщение;
   - `/cancel` — отменить многострочный ввод.

   Вопрос, ответ, вызов инструмента и результат инструмента имеют отдельные
   заголовки и цвета. Под ответом показывается расход токенов за все обращения
   к API для этого ответа, а также накопленный расход за весь диалог
   (всего, вход и выход). Статистика отделяется от ответа пустой строкой,
   начинается с `>>>` и выделяется синим цветом. Цвета отключаются при перенаправлении stdout,
   через `NO_COLOR=1` или `TERM=dumb`.

   Если модель запросила обновление памяти и приложение успешно сохранило слой,
   под ответом появляются отметки:

   ```text
   📝 Рабочая память обновлена
   🧠 Долговременная память обновлена
   ```

   Показываются только сохранённые слои. Для `null` и пустого patch отметок нет;
   при частичной ошибке отмечается только успешно сохранённый слой. Отметки
   сохраняются в метаданных истории и отображаются при следующем запуске,
   но не входят в текст ответа и промпт модели.

   Сообщения вводятся после запуска. Текст запроса в аргументах не принимается.
   При перенаправлении stdin действуют те же правила чата: каждая строка —
   отдельное сообщение, многострочный текст оформляется через `/multi` и `/send`.
   Конец ввода завершает диалог; незавершённый многострочный ввод не отправляется.

3. Проверка сборки без обращения к API:

   ```bash
   go build ./...
   ```

Для краткой справки используйте `go run ./cmd/llm-console --help`.

## Настройки

| Параметр | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `api_key` | Ключ DeepSeek API | обязательно |
| `base_url` | Адрес OpenAI-совместимого API | `https://api.deepseek.com` |
| `model` | Идентификатор модели | `deepseek-flash` |
| `profile` | Единственный статичный профиль агента: объект с `name` и `description`; задаёт поведение и правила консультации независимо от наличия задачи | не задан |
| `history_path` | Файл истории; относительный путь считается от каталога конфигурации | `history.json` |
| `working_memory_path` | Файл рабочей памяти | `working-memory.json` |
| `long_term_memory_path` | Файл долговременной памяти | `long-term-memory.json` |
| `task_path` | Файл состояния конечного автомата задачи; относительный путь считается от каталога конфигурации | `task.json` |
| `workflows` | Объект настроенных процессов: ключ — имя процесса, значение — его описание, условия активации и граф шагов | пустой набор процессов; обычный чат |
| `api_response_log_path` | JSONL-лог проблемных ответов API; `-` отключает запись; путь относительно каталога конфигурации | `api-responses.jsonl` |
| `timeout_seconds` | Максимальное время HTTP-запроса | `60` |
| `max_tokens` | Максимальное число токенов в ответе основного чата; `0` — не передавать ограничение. К суммаризации не применяется | не задан |
| `temperature` | Управляет случайностью ответа основного чата: число от `0` до `2`; если поле отсутствует или равно `null`, используется значение провайдера. Поддержка зависит от модели. К суммаризации не применяется | не задан |
| `thinking` | Режим рассуждений основного клиента: `enabled` или `disabled`; пустое значение — не передавать. В текущем чате с `tool_choice: required` принудительно используется `disabled`. К суммаризации не применяется | не задан |
| `reasoning_effort` | Уровень рассуждений основного клиента; значения зависят от провайдера и модели. Пустое значение — не передавать. В текущем чате с `tool_choice: required` параметр не передаётся. К суммаризации не применяется | не задан |

Каждый элемент `workflows` содержит следующие настройки:

| Поле процесса | Назначение | Обязательность |
| --- | --- | --- |
| `description` | Непустое описание назначения процесса | обязательно |
| `activation` | `startup` — активировать при загрузке агента с пустым состоянием задачи; `on_request` — запускать по просьбе пользователя в разговоре | обязательно |
| `trigger` | Непустое описание просьбы пользователя, по которой модель выбирает этот процесс; также используется для новой задачи после завершения предыдущей | обязательно для обоих режимов |
| `task` | Начальная цель задачи при автоматической активации | обязательно для `startup`; не используется для `on_request` |
| `initial` | Имя начального незавершённого шага из `steps` | обязательно |
| `steps` | Объект шагов процесса; каждый шаг задаёт этап, ожидаемое действие, инструменты и допустимые переходы | обязательно |

Допустим только один процесс с `activation: "startup"` на агента. Сохранённая
задача восстанавливается без повторного запуска, в том числе если она уже
завершена. Для `on_request` исходное сообщение пользователя становится целью
задачи; команда `/task start` не требуется. Смысл просьбы распознаёт модель,
допустимость выбранного процесса и переходов проверяет код.

В примере барбершопа `profile.description` описывает консультацию,
а `workflows.booking` — только запись с `activation: "on_request"`.
Просьба «проконсультируйте и запишите» использует ту же задачу `booking`;
отдельная задача консультации не нужна. Пример разработки использует
`workflows.development` с `activation: "startup"` и начальной целью `task`.
Структура `steps`, переходов и примеры конфигураций описаны в разделе
[«Задачи и конечный автомат»](#задачи-и-конечный-автомат).

Все файлы данных, включая `task_path`, должны находиться внутри каталога
конфигурации и отличаться друг от друга и от `config.json`.

Основные запросы завершаются вызовом служебной функции `submit_response`.
Её аргументы содержат `answer`, `working_memory`, `long_term_memory`.
Описание параметров в JSON Schema находится в `internal/app/response_tool.go`,
а инструкция работы с памятью и проверка аргументов — в
`internal/app/memory_client.go`. Текст ответа в консоли и истории берётся из `answer`; отметки сохранения памяти
добавляет приложение отдельно.

Приложение отправляет `tool_choice: "required"`: модель должна вызвать
инструмент вместо обычного текстового ответа. В основных запросах принудительно
используется `thinking: {"type":"disabled"}`, а `reasoning_effort` не передаётся:
DeepSeek не поддерживает обязательный выбор инструмента в thinking-режиме.
Это описано в [справочнике API](https://api-docs.deepseek.com/api/create-chat-completion/).
В запросах суммаризации thinking также явно отключён, а `reasoning_effort`
не передаётся. Значения `thinking` и `reasoning_effort` сохраняются в конфигурации
основного клиента, но к суммаризации не применяются; обязательный инструмент
основного чата также переопределяет их указанным выше образом.
Параметр `response_format` не передаётся.

`submit_response` завершает ход локально: результат этого вызова не отправляется
обратно модели. Если другие инструменты не нужны, ответ и обновления памяти
получаются за одно обращение к API. Если нужен калькулятор, время или длина
текста, модель сначала вызывает их, получает результаты обычным циклом tools,
затем отдельно вызывает `submit_response`. Поэтому такой пользовательский ход
может включать несколько обращений к API, но сохранение памяти не добавляет
своего запроса.

Аргументы проверяются локально: обязательные поля, непустые строки, статусы,
категории ключей и конфликты операций. Beta strict-mode не включён, поэтому
валидность аргументов не предполагается заранее. Неверный или обрезанный вызов
отклоняется без записи хода в историю и без изменения памяти; usage учитывается.
Обычный текст вместо `submit_response`, несколько финальных вызовов или смешение
финального и обычных инструментов в одном ответе также считаются ошибкой.
Повторных запросов для исправления нет. `max_tokens` ограничивает генерацию,
включая аргументы с планом и facts; для длинных задач увеличьте его или задайте `0`.

Приложение читает настройки из `config.json` выбранной директории агента.
Директория выбирается через `--dir` при запуске или `/agent` в чате.

## Изолированные агенты

Каждая директория агента содержит собственный `config.json`, профиль поведения,
процессы и состояние задачи, историю, саммари, рабочую и долговременную память,
счётчик токенов и лог API.
Настройки API также независимы: агенты могут использовать разные модели и ключи.
Файлы данных должны находиться внутри каталога конфигурации и отличаться друг
от друга и от конфигурации. Это разделение состояния приложения; инструменты
модели не получают отдельной песочницы операционной системы.

Создайте директории и скопируйте пример настроек, затем укажите ключи и профиль:

```bash
mkdir -p agents/mentor agents/writer
cp config.example.json agents/mentor/config.json
cp config.example.json agents/writer/config.json
go run ./cmd/llm-console --dir agents/mentor
```

`--dir` по умолчанию равен `.`. Настройки всегда читаются из `config.json`
в этой директории. Относительные пути файлов данных считаются от директории
агента. Конфигурация должна существовать; отсутствующие файлы истории
и памяти означают пустой контекст. При отсутствии файла задачи активируется
startup-процесс, если он настроен; иначе агент начинает работу как обычный чат.

В чате переключайтесь без перезапуска:

```text
/agent
/agent agents/writer
/profile
/agent agents/mentor
```

Пути `/agent` считаются от каталога запуска приложения; допускаются пробелы
в названии директории. Команда открывает `config.json` в указанной директории.
При первом переключении загружаются настройки и данные, при возвращении
используется уже открытый сеанс, включая несохранённое состояние после ошибок
записи. Чтобы перечитать изменённые вручную настройки или файлы, перезапустите
приложение. Неудачное переключение оставляет текущего агента активным.
Переписка, память и расход токенов между агентами не переносятся. `/clear`
и `/memory` работают только с текущим агентом. Старая переписка остаётся
в прокрутке терминала. Одновременная работа нескольких процессов с одной
директорией агента не поддерживается.

## Статичный профиль поведения

Поле `profile` в конфигурации задаёт один профиль агента:

```json
{
  "profile": {
    "name": "mentor",
    "description": "Отвечай на русском, подробно объясняй решение и показывай примеры кода."
  }
}
```

Это фрагмент конфигурации: добавьте его к настройкам API. `name` — непустое
имя без пробелов, `description` — непустое описание поведения.
Отсутствующий `profile` или `null` означает работу без статичного профиля.
Массив `profiles` и `active_profile` больше не используются; замените их одним
объектом `profile` вручную. Автоматической миграции нет.

`/profile` показывает профиль текущего агента без обращения к API. Чтобы сменить
поведение вместе с контекстом, переключите агента. Изменения конфигурации
загружаются после перезапуска; модель не редактирует профиль.

Описание передаётся отдельной системной инструкцией в каждый основной запрос,
включая запросы после сжатия истории; в суммаризацию оно не включается.
Профиль определяет формат текста `answer`, сохраняет протокол `submit_response`
и имеет приоритет над предпочтениями из памяти и старой переписки.
`/clear` сохраняет профиль. Долговременные facts `profile.*` содержат сведения
о пользователе и отличаются от статичной инструкции поведения; описание
профиля не копируется в память.

## Диагностика ответов API

Проблемные HTTP-ответы API дописываются в `api-responses.jsonl` рядом с
конфигурацией. Успешные ответы не записываются. Логирование действует для
основного диалога, раундов инструментов и суммаризации. Параметр
`api_response_log_path` меняет путь; значение `-` отключает запись.
Файл лога должен отличаться от конфигурации и всех файлов памяти.

Одна строка содержит только время UTC (`time`), HTTP-статус (`http_status`),
категорию проблемы (`error`) и полное тело ответа в строковом поле `body`.
Сохраняются пробелы, невалидный JSON и частично прочитанное тело.
Настройки конфигурации, данные запросов и HTTP-заголовки в лог не попадают.
Если HTTP-ответ не получен, записывать нечего: транспортная ошибка показывается
в консоли без записи в этот лог.

Категории проблем: `http_error`, `invalid_json`, `read_response`,
`invalid_response`, `no_choices`, `empty_answer`, `truncated_answer`,
`incomplete_response`, `unexpected_tool_calls`, `invalid_tool_call`,
`tool_call_limit`, `missing_final_tool`, `invalid_final_tool`,
`invalid_final_arguments`, `incomplete_final_arguments`. Последние четыре означают отсутствие обязательного
`submit_response`, неверный набор вызовов или невалидные аргументы финальной
функции либо незавершённый JSON аргументов. Даже при `finish_reason=tool_calls`
API может вернуть оборванные аргументы: приложение блокирует такой ответ до
проверки инвариантов, не применяет память и не дописывает JSON за модель.
Повторный запрос автоматически не выполняется. Исходное тело ответа сохраняется целиком. `finish_reason`, usage,
`tool_calls` и аргументы функций можно посмотреть внутри `body`.

Права файла — `0600`, лог по умолчанию исключён из Git. При другом имени добавьте
его в `.gitignore`. Ошибка записи показывается в stderr и не отменяет ответ;
ошибка открытия лога останавливает запуск.

В основных запросах пустой `content` допустим, если ответ содержит вызов
инструмента. Если `submit_response` и другие вызовы отсутствуют, ход отклоняется
как `missing_final_tool`. Текстовые ответы без инструментов допустимы только
для суммаризации. Для неё пустой ответ даёт `empty_answer` с диагностикой
`finish_reason` и размерами содержимого.

`finish_reason: length` означает обрезанный ответ: проверьте `max_tokens` и usage.
Обрезанные аргументы не выполняются. Ответы с `content_filter`, `aborted` или
`insufficient_system_resource` также отклоняются. Рассуждения не подставляются
вместо финального ответа. Автоматических повторов нет.
Для разбора сбоя найдите запись по времени и посмотрите `body`.

## История диалога

По умолчанию история хранится в `history.json` рядом с конфигурацией.
Другой файл можно указать через `history_path`. При запуске восстанавливаются
контекст и общий расход токенов. Сохранённая переписка сразу выводится в консоль:
вопросы, ответы, вызовы инструментов и их результаты оформляются как в текущем
диалоге. Под каждым ответом показываются те же строки с `>>>`: расход за
этот ответ и общий расход на тот момент, с теми же отступами и цветом.
После переписки появляется приглашение ввода. Показ истории не вызывает API
и не увеличивает расход токенов.

Если файла нет, начинается новый диалог.

После каждого успешного ответа сохраняются вопросы пользователя, сообщения
ассистента, вызовы инструментов (имя, аргументы, ID), результаты инструментов
и статистика токенов каждого ответа с накопленным итогом на тот момент. Поле `reasoning_content`, если модель его
вернула, тоже сохраняется. Системная инструкция работы с памятью добавляется
при каждом основном запросе и в историю не записывается.

Контекст автоматически суммаризируется перед очередным запросом, когда после
предыдущего саммари накопилось 10 пользовательских запросов. Ответы ассистента,
вызовы и результаты инструментов учитываются в содержании саммари, но не
в счётчике запросов. Первое саммари создаётся перед 11-м запросом пользователя. При обновлении модель получает предыдущее саммари и новые
сообщения; после обновления обычный запрос содержит саммари и текущий вопрос.
Между обновлениями к ним добавляются ещё не сжатые сообщения.

Саммари хранится отдельно в поле `summary`: `content` содержит текст,
`message_count` — количество записей массива `messages`, уже вошедших в него
(включая сообщения инструментов). Полная переписка сохраняется и отображается
как прежде; служебный запрос и саммари в неё не добавляются. После перезапуска
саммари и граница сжатия восстанавливаются. `/clear` сбрасывает и саммари.

Суммаризация — отдельный текстовый запрос к той же модели без инструментов
и JSON-режима. Предыдущее саммари и новые сообщения передаются массивом
с сохранением ролей, вызовов и результатов инструментов и `reasoning_content`,
если оно есть. История не упаковывается в текст одного сообщения.
Для суммаризации явно задан `thinking: {"type":"disabled"}`. Параметры
генерации основного чата из конфигурации, включая `max_tokens` и `temperature`,
к этому запросу не применяются; `reasoning_effort` не передаётся. Общими
остаются модель, подключение и таймаут HTTP-запроса.
Её токены входят в общий расход диалога.
Если суммаризация не удалась, вопрос не отправляется, прежний контекст остаётся
доступным, а следующая попытка повторяет суммаризацию.

## Модель памяти

Поля задачи в рабочей памяти — заметки модели. Они не управляют конечным
автоматом: его состояние, правила переходов и подтверждения хранятся отдельно,
см. раздел «Задачи и конечный автомат» ниже.

Слои хранятся в отдельных файлах. Относительные пути считаются от каталога
конфигурации; все три пути должны отличаться. Отсутствующий файл означает пустой
слой. В основном запросе оба настроенных слоя присутствуют всегда; пустой
обозначается `null`. Модель может заполнить рабочую память по подтверждённым данным
текущего запроса и доступной переписки; отсутствующие сведения она должна уточнять.
Все сохранённые слои загружаются при запуске. Удаление файла во время работы
не меняет уже загруженное состояние: используйте `/memory clear working` для
сброса без перезапуска или перезапустите приложение после удаления файла.

| Слой | Что сохраняется и как | Хранилище | Правило включения в промпт |
| --- | --- | --- | --- |
| Краткосрочная память | Успешные ходы диалога и взаимодействия с инструментами; саммари после каждых 10 пользовательских запросов | `history.json` | Саммари и ещё не сжатые сообщения, затем текущий вопрос; до первого саммари — вся переписка |
| Рабочая память | Контекст разговора: рабочая цель, план, стадия, статус, временные сведения, результаты и открытые вопросы; жизненный цикл независим от workflow | `working-memory.json` | Полный снимок отдельным системным JSON-блоком; пустой слой передаётся как `null` |
| Долговременная память | Модель автоматически выделяет подтверждённый профиль (`profile.*`), знания (`knowledge.*`), списки решений (`decision.*`) и изменений (`history.*`) | `long-term-memory.json` | Все сохранённые facts отдельным системным JSON-блоком; пустой слой передаётся как `null` |

Долговременная память хранит `facts` отдельно от переписки: каждому ключу
соответствуют `entries` со значением `value` и временем `recorded_at`.
Модель сама выбирает, что относится к рабочему контексту, а что должно
сохраниться надолго. Она получает
текущую память и передаёт ответ вместе с её изменениями аргументами одного
финального вызова `submit_response`:

```json
{
  "answer": "Учту русский язык. Для задачи составлен план; сейчас разбираем требования.",
  "working_memory": {
    "task": "Разработка консольного ассистента",
    "plan": ["Уточнить требования", "Реализовать память", "Проверить сборку"],
    "current_stage": "Уточнить требования",
    "status": "in_progress",
    "facts": {"goal": "Разделить память на три слоя"}
  },
  "long_term_memory": {
    "upsert": {"profile.language": {"value": "Русский"}},
    "delete": []
  }
}
```

- `answer` — непустой текст для пользователя.
- `working_memory: null` оставляет рабочий контекст без изменений. Объект заменяет снимок
  целиком: `task`, полный `plan`, `current_stage`, `status`, `facts` обязательны.
  Поле `task` обозначает цель рабочего контекста, не идентификатор задачи workflow.
  План сохраняет все шаги, включая уже завершённые; статус — `in_progress`,
  `blocked` или `completed` — относится к рабочей цели. Она может существовать
  без workflow и охватывать несколько процессов. Завершение, отмена и запуск
  процесса не меняют рабочую память автоматически; завершённый процесс,
  загруженный при запуске приложения, также её не очищает. Статус `completed`
  сохраняет рабочие факты. При следующем обновлении модель исключает сведения,
  которые перестали быть нужны по подтверждённым данным, и сохраняет полезный
  контекст. Полностью заменить или очистить его можно командами памяти.
- `long_term_memory: null` оставляет facts без изменений. Объект содержит
  независимые необязательные операции: `upsert` для добавления и замены по ключу
  (значение операции — объект с `value`, для списка также `item_id`),
  `delete` для явно отменённых или опровергнутых фактов. Пропущенный `upsert`
  означает `{}`, пропущенный `delete` — `[]`; явный `null` вместо операции
  недопустим. Неупомянутые ключи сохраняются. Один ключ нельзя одновременно
  добавлять и удалять. Пустой объект `{}` не меняет долговременную память.

Правила долговременных фактов задаются категорией ключа:

| Ключ | Обновление | Срок хранения |
| --- | --- | --- |
| `profile.*` | Одно актуальное значение профиля или предпочтения заменяется новым | До явного удаления |
| `knowledge.*` | Одно актуальное знание, срок, статус или версия заменяется новым | До явного удаления |
| `decision.*` | Решения накапливаются списком; одинаковый `item_id` исправляет существующий элемент | После завершения задачи сохраняется |
| `history.*` | События изменений накапливаются списком; одинаковый `item_id` исправляет существующий элемент | После завершения задачи сохраняется |

Для списков передавайте, например:

```json
{
  "upsert": {
    "decision.storage": {"item_id": "database", "value": "PostgreSQL"},
    "history.release": {"item_id": "release-2026-11-26", "value": "Выпущена новая сборка"}
  }
}
```

Новый `item_id` добавляет элемент списка, прежний заменяет только этот элемент.
Чтобы исправить выбор базы на SQLite, следует повторно передать
`decision.storage` с `item_id: "database"` и `value: "SQLite"`.
Временные сроки, статусы, ограничения и промежуточные результаты хранятся
только в `working_memory.facts`. Долговременная память принимает только четыре
категории из таблицы. Устойчивые сведения, которые должны сохраняться после
завершения работы, относятся к `knowledge.*`, а принятые решения — к `decision.*`.

Рабочая память, долговременная память и автомат имеют независимые жизненные
циклы. Завершение workflow не удаляет факты из памяти. Временные рабочие
сведения удаляются при явном `/memory forget working`, очистке слоя,
замене рабочего контекста или когда модель исключает их из полного снимка
как больше не нужные. Для удаления долговременного факта нужна явная команда
или операция `long_term_memory.delete`.

Время назначает приложение в UTC, а не модель. Для обновлений модели берётся
время начала запроса, для ручных команд — время команды. Каждый элемент
имеет `recorded_at`; замена разрешена только при строго более позднем времени.
При равном времени сохранённое значение остаётся. Более ранний ответ не может
перезаписать новое значение. `deleted_at` хранит время удаления ключа и
защищает от его восстановления устаревшим обновлением.

Замены фиксируются в `changes`: ключ, `before`, `after`, время и причина.
Удаления также записываются (`after: null`). Факты и журнал сохраняются одним
атомарным обновлением файла `long-term-memory.json`: при ошибке записи
состояние и журнал в приложении не меняются. Просмотр журнала — `/memory log`.
Журнал и отметки удаления не передаются модели, поэтому отменённые значения
не попадают в контекст из журнала. Журнал сохраняет прежние значения даже после
`/memory forget` и `/memory clear long`; эти команды очищают действующие факты.
Для полного удаления журнала нужно удалить файл долговременной памяти при
остановленном приложении.

Смысловое сопоставление противоречий выполняет модель по инструкции:
использовать существующий ключ и ID, а не добавлять рядом синоним.
Код гарантирует разрешение конфликта по времени для совпадающих ключей и ID;
автоматическое распознавание произвольных противоречий между разными ключами
не выполняется.

Файлы памяти используют только текущую структуру: старые строковые значения
`facts` не читаются, миграций и поля версии формата нет. Перед запуском с прежними
файлами памяти их нужно сохранить отдельно и убрать из каталога агента;
история диалога не меняет свой формат.

Инструкция модели запрещает принимать её предположения и предложения за
подтверждённые сведения, отмечать запланированные действия выполненными и
сохранять секреты. Реальный прогресс определяется по запросу и результатам
инструментов; временные детали идут в рабочую память. Например, сообщение
«Запомни: я предпочитаю русский» может автоматически обновить `profile.language`,
а «Сборка прошла, переходим к документации» — план и текущую стадию.
Выбор содержимого выполняет модель; приложение проверяет формат и применяет
выбранные операции. Это не гарантирует безошибочность смыслового выбора модели.

Обновление памяти не требует отдельных LLM-запросов. При вызове обычных
инструментов сохраняется цикл `tool_calls`: `submit_response` вызывается
после их результатов. Служебный вызов не передаётся исполнителю инструментов,
не выводится отдельным блоком UI и не записывается как незавершённый tool_call:
в историю попадает обычное итоговое сообщение с текстом `answer`. Суммаризация истории остаётся отдельным периодическим запросом;
она не обновляет другие слои. Её клиент получает обычный текст без инструкции формата памяти.

В промпт сначала попадает инструкция формата и обновления памяти, затем
правила автомата, доступные процессы и актуальное состояние задачи,
активный статичный профиль (если выбран),
долговременные facts, текущая задача, саммари с новыми сообщениями и текущий
вопрос. Блоки памяти помечены как данные, а не инструкции. Текущий запрос имеет
приоритет, данные текущей задачи имеют приоритет над долговременными.
Статичный профиль имеет приоритет над предпочтениями из памяти и старой
переписки; служебный протокол ответа и правила памяти сохраняются.
Статистика токенов, отметки сохранения памяти и служебные JSON-ответы
в контекст модели не включаются.

Сначала проверяются все аргументы `submit_response`, затем каждый изменяемый слой сохраняется через
временный файл и замену основного. Запись слоёв независима: если один файл
недоступен, другой может обновиться. Не сохранённый слой остаётся в прежнем
состоянии, консоль показывает ошибку вместе с текстом ответа; сам ответ остаётся
в диалоге. Автоматического повторного запроса или повторного применения patch нет.

Ручные команды остаются для просмотра и исправлений без обращения к API:

```text
/memory show
/memory task Разработка консольного ассистента
/memory set working goal Разделить память на три слоя
/memory set long profile.language Русский
/memory set working deadline Пятница
/memory add decision.storage database PostgreSQL
/memory add decision.storage database SQLite
/memory log
/memory complete
/memory forget long profile.language
/memory clear working
/memory clear long
```

`/memory task` задаёт новую рабочую цель с начальным планом из одного шага и
заменяет прежнюю рабочую память. `/memory complete` отмечает рабочую цель
завершённой без API и сохраняет её факты; команда доступна и при активном
workflow, состояние которого она не меняет. `/memory set` заменяет
одиночное значение по ключу, `/memory add` добавляет или исправляет элемент списка,
`/memory forget` удаляет запись. `/memory clear working` очищает рабочий контекст целиком,
`/memory clear long` — все долговременные facts. `/clear` удаляет только диалог,
саммари и статистику токенов. При следующем вопросе модель снова может обновить
память по текущей задаче и запросу.

Удаление факта из слоя не стирает упоминания в диалоге и саммари. Чтобы убрать
их из краткосрочного контекста, используйте `/clear`. Для сброса действующей памяти нужны
`/clear`, `/memory clear working`, `/memory clear long`. Журнал изменений
при этом остаётся в файле долговременной памяти.

Рабочий файл содержит поля снимка `task`, `plan`, `current_stage`, `status`,
`facts`; долговременный — `facts`, журнал `changes` и отметки удаления `deleted_at`.
Форматы файлов не версионируются:
поля `version` и проверки номера версии отсутствуют. Приложение работает только
с текущей структурой данных, без миграций и поддержки старых форматов.
История всегда использует саммари с новыми сообщениями.

Запись выполняется через временный файл с последующей заменой основного.
При ошибке сохранения ответ всё равно показывается, контекст остаётся в памяти,
а консоль сообщает, что история не сохранена. Если API вернул ошибку, ход не
добавляется в переписку, но уже полученная статистика токенов сохраняется.

Команда `/clear` удаляет файл истории и сбрасывает контекст и счётчик токенов.
После неё можно сразу продолжить общение с чистого диалога.
Если удалить файл не удалось, контекст и счётчик остаются без изменений.
Уже выведенные сообщения остаются в прокрутке терминала.

Повреждённый JSON или некорректные данные истории останавливают запуск:
существующий файл автоматически не перезаписывается. Для нового диалога
переместите повреждённый файл или выберите другой `history_path`.

Формат файла:

```json
{
  "messages": [
    {"role": "user", "content": "Привет"},
    {
      "role": "assistant",
      "content": "Здравствуйте!",
      "usage": {"prompt_tokens": 10, "completion_tokens": 5, "total_tokens": 15},
      "total_usage": {"prompt_tokens": 10, "completion_tokens": 5, "total_tokens": 15}
    }
  ],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 5,
    "total_tokens": 15
  }
}
```

В итоговом сообщении ассистента `usage` — расход за весь шаг, включая обращения
с инструментами; `total_usage` — общий расход на момент этого ответа.
Статистика не отправляется модели: перед запросом извлекаются только поля
сообщения для API. Верхнеуровневый `usage` хранит текущий общий расход,
включая полученную статистику неуспешных шагов.

`history.json`, `working-memory.json`, `long-term-memory.json` и временные
файлы исключены из Git. При выборе других имён добавьте их в `.gitignore`.

## Архитектура

`cmd/llm-console/main.go` запускает чат, `session.go` собирает зависимости
и управляет изолированными сеансами агентов, `args.go`
разбирает параметры запуска, `console.go` обрабатывает ввод и оформление.
Сценарий диалога и контекст в памяти находятся в
`internal/app/ChatService`; его можно вызвать из desktop-интерфейса без
копирования логики. Контракт `llm.Client` отделяет сервис от API-провайдера.
Пакет `internal/history` отвечает за JSON-историю, `internal/memory` — за
раздельное хранение рабочей и долговременной памяти. `internal/app/memory.go`
задаёт команды записи и правила включения слоёв в промпт.
`internal/app/response_tool.go` задаёт JSON Schema служебной функции
`submit_response`, `internal/app/memory_client.go` — инструкцию автоматического
обновления памяти и проверку аргументов. Адаптер возвращает обычный текст
и типизированные изменения в `llm.Result`; `ChatService` применяет их.
`ChatService` управляет перепиской и общим расходом токенов через контракт
`HistoryStore`; консоль отвечает только за ввод и отображение.

После каждого ответа показывается расход токенов за текущий шаг и за весь
диалог: общее число, входные и выходные токены. Счётчик сохраняется
вместе с перепиской и сбрасывается командой `/clear`. Учитываются все обращения к API, включая
повторную отправку контекста после вызовов инструментов. Если шаг завершился
ошибкой, уже полученная статистика также учитывается.
Суммы строятся по данным `usage` от API: обращения, для которых статистика
не пришла, в сумму не входят. Если данных совсем нет, выводится
«данные недоступны».

## Инструменты модели

В основной запрос передаются функции в формате OpenAI-compatible
`tools`. Три обычных инструмента модель использует по необходимости:

- `current_time` — текущие дата и время в UTC, без аргументов;
- `calculate` — арифметика: `operation` (`add`, `subtract`, `multiply`,
  `divide`) и два числа `a`, `b`;
- `text_length` — количество кодовых точек Unicode в строке `text`.

Служебная функция — `submit_response`: обязательный финальный ответ с
обновлениями памяти. Её обрабатывает сервис диалога без дополнительного
обращения к модели.

Если у агента настроены процессы задач, также доступны `task_start` и
`task_action`. Их выполняет движок задач с проверкой правил процесса.

При вызове обычного инструмента его имя и аргументы выводятся отдельным блоком
до выполнения. Результат (включая ошибку инструмента) показывается следующим блоком.
Сообщения чата и события инструментов выводятся в stdout. Ошибки запуска
выводятся в stderr; ошибки запросов показываются в чате, после них можно
продолжить диалог. Неуспешный ход не добавляется в контекст.

Для обычных инструментов приложение проверяет аргументы, выполняет вызовы
и отправляет результаты обратно модели. Ошибки инструментов также передаются модели. Поддерживается
несколько вызовов за ответ; для одного пользовательского запроса ограничение —
10 обращений к API. Расход токенов суммируется по полученным ответам API.
Поддержка вызова инструментов зависит от выбранного провайдера и модели.
Например, после запуска задайте в чате вопрос: «Сколько будет 123 умножить на 456?»

## Задачи и конечный автомат

Задача необязательна. Конфигурация `"workflows": {}` оставляет агента обычным
чатом. Для процессов с задачами настройте `workflows` в конфигурации агента:

- `activation: "startup"` — задача активна сразу после загрузки агента с пустым
  состоянием задачи; начальная цель берётся из `task`. Допустим один такой процесс.
- `activation: "on_request"` — агент общается свободно и вызывает `task_start`,
  когда пользователь просит выполнить действие из `trigger`. Ручная команда
  запуска не требуется. У всех процессов `trigger` также описывает запрос для
  запуска новой задачи после завершения предыдущей.

Например, агент разработки сразу начинает с уточнения требований и подготовки
плана. Администратор барбершопа консультирует в обычном чате; просьба
«Запишите меня на стрижку» запускает запись. Если пользователь сразу просит
консультацию и запись, агент консультирует по профилю и использует тот же процесс
`booking` для записи. Уже полученные сведения остаются в переписке и памяти;
отдельного процесса консультации нет.

Готовые конфигурации:

- `examples/developer/config.example.json` — `development`, активация при загрузке:
  planning → execution → validation → done.
- `examples/barbershop/config.example.json` — `booking`, активация по просьбе
  пользователя: сбор данных, подтверждение параметров и оформление записи.
  Консультация определяется профилем агента.

Скопируйте выбранный пример в `config.json` отдельного агента, задайте его ключ
API и запустите приложение с `--dir` этой директории. В примерах только заглушка
ключа. Корневой `config.example.json` настроен для обычного чата.

Каждый процесс содержит `description`, `activation`, `trigger`, `initial` и
конечный набор `steps`. Для startup-процесса также обязательна `task`.
Каждый шаг задаёт:

- `stage` — этап задачи;
- `expected_action` — ожидаемое действие и его исполнитель;
- `tools` — разрешённые обычные инструменты; пустой список запрещает их все;
- `actions` — допустимые действия и переходы из текущего шага;
- `terminal: true` — конечный шаг без действий и инструментов.

Действие содержит `actor` (`assistant` или `user`), целевой шаг `to`, список
разрешённых к изменению полей `fields`, обязательные данные `required` и
очищаемые поля `clear`. Вначале очищаются перечисленные поля, затем применяются
изменения, проверяется наличие обязательных значений и выполняется переход.
Переход в тот же шаг позволяет собирать данные частями. Возврат к планированию
или параметрам записи задаётся явным переходом с очисткой зависимых результатов.

`task_start` принимает имя настроенного процесса. Код проверяет, что есть текущий
запрос пользователя, задача ещё не активна и в этом ходе не было другого успешного
запуска; исходный запрос становится названием задачи. Распознавание смысла просьбы
выполняет модель по `trigger`. Это семантическое решение может быть ошибочным;
допустимые процессы, начальный шаг и последующие переходы проверяет код.
Модель не может подменить текущую задачу, выбрать произвольный начальный шаг
или создать свой граф переходов.

Модель передаёт действие через `task_action`:

```json
{"action":"present_plan","fields":{"plan":"Согласованный порядок работы"}}
```

Код проверяет текущее состояние, имя действия, исполнителя и разрешённые поля
до записи. Перед вызовом каждого обычного инструмента отдельно проверяется
разрешение для текущего шага — даже если модель прислала скрытый или запрещённый
вызов. Смена состояния сама по себе не выполняет внешнюю операцию.

Пользовательские подтверждения отделены от действий модели: план утверждается
командой `/approve`, модель вызвать её аналог не может. После подтверждения
план или время записи нельзя изменить действием, которому эти поля недоступны.
Для изменения нужно вернуться на предыдущий шаг и подтвердить параметры снова.
Завершение ответа через `submit_response` доступно на любом шаге и завершает
только ход разговора; задача завершается лишь на конечном шаге автомата.

Текущие инструменты приложения не изменяют исходники, не запускают сборку и
не подключены к расписанию барбершопа. Поэтому в примерах результат разработки
проверяет пользователь, а запись создаётся во внешней системе вручную:

```text
/approve
/task action validate {"validation_report":"Сборка и ручная проверка выполнены успешно"}
/task action register {"booking_id":"Идентификатор реально созданной записи"}
```

Эти действия допустимы только на соответствующих шагах. Движок проверяет
наличие данных, но не подтверждает достоверность отчёта пользователя.
Свободный текст ответа также не является доказательством выполнения операции.
Для автоматического выполнения потребуются реальные инструменты с проверкой
результата перед переходом. Настроенный граф гарантирует допустимость порядка
действий, но не гарантирует, что пользователь даст все сведения или внешняя
операция когда-либо станет доступна.

Просмотр и ручное управление без обращения к API:

```text
/task
/task list
/task cancel
/task start booking Записаться на стрижку
```

Последняя команда — дополнительный ручной способ запуска. Обычный сценарий
использует startup-настройку или просьбу в разговоре.

Состояние хранится в `task.json` (`task_path` в конфигурации): имя процесса,
цель, текущий шаг и данные. Этап, ожидаемое действие и признак завершения
вычисляются из описания шага. Отсутствующий файл или `null` означает отсутствие
задачи. У каждого агента своё хранилище; переключение через `/agent` восстанавливает
его состояние. `/clear` и команды памяти не изменяют автомат.
Завершённая задача остаётся доступной для просмотра, а общение возвращается в
режим чата до следующей просьбы. `/task cancel` возвращает в чат; startup-процесс
вновь активируется при следующей загрузке агента с пустым состоянием.

При загрузке проверяются шаги, ссылки переходов, достижимость из `initial` и
наличие пути к завершению для каждого шага. Запись задачи выполняется через
временный файл и замену основного; при ошибке сохранения переход не применяется.
Успешный переход сохраняется сразу, поэтому последующий сбой API или некорректный
`submit_response` не откатывает его. В следующем ходе модель получает актуальное
состояние отдельно от истории и саммари.

### Инварианты барбершопа

Эти инварианты относятся к агенту — администратору барбершопа: часы работы
заведения. Ограничения по полу или категории клиента нет. `invariants.example.json` —
пример правил именно для барбершопа, а не общие ограничения всех ассистентов.

Правила загружаются автоматически из `invariants.json` в директории агента.
При запуске и переключении агента приложение показывает действующий снимок
правил после вывода истории. Для каждого запроса актуальные правила передаются
заключительным системным сообщением: прежние часы и отказы в переписке, саммари
или памяти не определяют допустимость записи. При смене правил модель должна
пересчитать допустимость времени и обновить устаревшие выводы в рабочей памяти.
Начальный файл создаётся из `invariants.example.json`; значения задаются в файле,
в коде начальных значений нет. Для просмотра и явного изменения:

```text
/invariant
/invariant set working_hours.end 20:00
/invariant history
```

В примере файла: обслуживание полностью между 10:00 и 19:00. Ключи изменения: `working_hours.start`, `working_hours.end`
(строго `HH:MM`, начало раньше окончания). Ночной график не поддерживается. Время — местное время заведения.
Изменения в обычном диалоге,
памяти, профиле и `/clear` не меняют инварианты.

`invariants.json` в директории агента хранит текущие `rules` и журнал `changes`
с временем, ключом, старым и новым значением и источником `user_command`.
Они записываются одной атомарной заменой файла, чтобы правило не изменилось
без записи в журнале. Начальные значения задаются файлом с пустым журналом. Файл читается при
загрузке сеанса; модель не получает инструмента его изменения.

При включённых правилах `submit_response` содержит `barber_response`:

```json
{"kind":"booking","start":"18:00","duration_minutes":40}
```

Код проверяет длительность и весь интервал обслуживания, включая
окончание ровно в момент закрытия. Без внешней системы длительность услуги
оцениваем в 30–40 минут; для проверки окончания обслуживания резервируем 40 минут.
Пропущенная длительность и значения меньше 40 минут также считаются 40 минутами;
подтверждённая большая длительность учитывается целиком. У клиента длительность
не спрашиваем и уточнять её никуда не отправляем. Для недостающих сведений
модель выбирает `kind=clarify` и сама формулирует уточняющий вопрос в `answer`.
Клиента спрашивают об услуге, удобных дне и времени, при необходимости — для кого запись. Другие допустимые ответы:
`{"kind":"rules"}` и `{"kind":"refuse"}`. Правила и отказы при нарушении инвариантов формируются приложением.
Остальные реплики берутся из `answer` модели: `clarify` — уточнения,
`dialogue` — беседа и объяснение шага задачи, `booking` — обсуждение записи
с проверяемыми параметрами. После согласия пользователя модель учитывает
состояние workflow и объясняет следующий шаг, включая `/approve`, если требуется
подтверждение. Параметры записи проверяются кодом; соответствие свободного текста
этим параметрам код не проверяет.

Для процесса `booking` инварианты дополнительно проверяются внутри автомата
до сохранения каждого перехода: `task_action`, `/approve` и `/task action`
используют одну проверку. Проверяется кандидат состояния с объединёнными
полями, включая сохранённый `slot`; источник данных и согласие пользователя
не отменяют часы работы. Время `slot` задаётся строго в формате `HH:MM`.
Для расчёта окончания резервируется не менее 40 минут. Если в данных задачи
есть `duration_minutes`, учитывается и большая длительность. Без времени
можно находиться только на начальном шаге сбора данных. Недопустимый переход
не меняет ни состояние в памяти, ни файл задачи, даже если последующий
финальный ответ модели ещё не получен. При изменении инвариантов существующая
задача проверяется заново на следующем переходе. Возврат через `revise`,
очищающий время, и отмена остаются доступны для исправления старой задачи.
 Неподдерживаемые запросы получают отказ; это узкий сценарий
барбера, а не универсальный проверяющий произвольные архитектурные ограничения.
Предложение времени не создаёт запись и не проверяет наличие свободного места.


Рабочая и долговременная память обновляются по общим правилам после успешной
проверки ответа и инвариантов: рабочая память получает полный снимок задачи,
долговременная — операции `upsert`/`delete`. `null` означает отсутствие изменений
только в соответствующем слое. Если ответ некорректен или предложенная запись
нарушает часы работы, ответ блокируется до применения обоих обновлений памяти,
без повторного запроса. Память не управляет инвариантами. Загрузка слоёв,
ручные команды `/memory`, сохранение памяти при `/clear` и отдельная суммаризация
диалога сохраняют обычное поведение.
Без включения инвариантов сохраняется обычный режим диалога и памяти.
