# LLM Console

Консольное Go-приложение для диалога с LLM. Переписка сохраняется в JSON
и автоматически подгружается при следующем запуске.
Оно настроено на DeepSeek и использует его OpenAI-совместимый endpoint
`POST /chat/completions`.

## Запуск

1. Создайте файл конфигурации и внесите ключ. Он исключён из Git:

   ```bash
   cp config.example.json config.json
   ```

   В `config.json` укажите `api_key`. Остальные поля уже настроены на DeepSeek.

2. Запустите чат:

   ```bash
   go run ./cmd/llm-console
   ```

   После запуска открывается диалог:
   Enter отправляет сообщение, после ответа можно сразу задать следующий вопрос.
   В контекст попадают саммари и сообщения, ещё не вошедшие в него,
   а также рабочая и долговременная память.
   Полная переписка сохраняется и отображается при запуске.

   Команды чата:

   - `/exit` или `/quit` — выход (также Ctrl+D на пустой строке);
   - `/clear` — удалить диалог и саммари, сбросить расход токенов; рабочая и долговременная память сохраняются;
   - `/memory` — просмотр и ручное редактирование памяти;
   - `/profile` — показать активный статичный профиль;
   - `/profile list` — список профилей; `/profile use <имя>` — переключить;
   - `/profile show <имя>` — показать описание; `/profile off` — отключить профиль;
   - `/multi` — начать многострочное сообщение;
   - `/send` на отдельной строке — отправить многострочное сообщение;
   - `/cancel` — отменить многострочный ввод.

   Вопрос, ответ, вызов инструмента и результат инструмента имеют отдельные
   заголовки и цвета. Под ответом показывается расход токенов за все обращения
   к API для этого ответа, а также накопленный расход за весь диалог
   (всего, вход и выход). Статистика отделяется от ответа пустой строкой,
   начинается с `>>>` и выделяется синим цветом. Цвета отключаются при перенаправлении stdout,
   через `NO_COLOR=1` или `TERM=dumb`.

   Если модель запросила обновление памяти и приложение успешно сохранило слой,
   под ответом появляются отметки:

   ```text
   📝 Рабочая память обновлена
   🧠 Долговременная память обновлена
   ```

   Показываются только сохранённые слои. Для `null` и пустого patch отметок нет;
   при частичной ошибке отмечается только успешно сохранённый слой. Отметки
   сохраняются в метаданных истории и отображаются при следующем запуске,
   но не входят в текст ответа и промпт модели.

   Сообщения вводятся после запуска. Текст запроса в аргументах не принимается.
   При перенаправлении stdin действуют те же правила чата: каждая строка —
   отдельное сообщение, многострочный текст оформляется через `/multi` и `/send`.
   Конец ввода завершает диалог; незавершённый многострочный ввод не отправляется.

3. Проверка сборки без обращения к API:

   ```bash
   go build ./...
   ```

Для краткой справки используйте `go run ./cmd/llm-console --help`.

## Настройки

| Параметр | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `api_key` | Ключ DeepSeek API | обязательно |
| `base_url` | Адрес OpenAI-совместимого API | `https://api.deepseek.com` |
| `model` | Идентификатор модели | `deepseek-flash` |
| `profiles` | Статичные профили: массив объектов с `name` и `description` | пустой список |
| `active_profile` | Имя профиля при запуске; пустая строка отключает профиль | не задан |
| `history_path` | Файл истории; относительный путь считается от каталога конфигурации | `history.json` |
| `working_memory_path` | Файл рабочей памяти | `working-memory.json` |
| `long_term_memory_path` | Файл долговременной памяти | `long-term-memory.json` |
| `api_response_log_path` | JSONL-лог проблемных ответов API; `-` отключает запись; путь относительно каталога конфигурации | `api-responses.jsonl` |
| `timeout_seconds` | Максимальное время HTTP-запроса | `60` |
| `reasoning_effort` | Уровень рассуждений при суммаризации, например `low`, `medium` или `high`; пустая строка — не передавать. Поддержка и значения зависят от провайдера и модели | не задан |
| `max_tokens` | Максимальное число токенов в ответе; `0` — не передавать ограничение | не задан |
| `temperature` | Управляет случайностью ответа: число от `0` до `2`; если поле отсутствует или равно `null`, используется значение провайдера. Поддержка зависит от модели | не задан |
| `thinking` | Режим thinking при суммаризации в DeepSeek: `enabled` или `disabled`; если поле отсутствует или пусто, используется настройка провайдера | не задан |

Основные запросы завершаются вызовом служебной функции `submit_response`.
Её аргументы содержат `answer`, `working_memory`, `long_term_memory`.
Описание параметров в JSON Schema находится в `internal/app/response_tool.go`,
а инструкция работы с памятью и проверка аргументов — в
`internal/app/memory_client.go`. Текст ответа в консоли и истории берётся из `answer`; отметки сохранения памяти
добавляет приложение отдельно.

Приложение отправляет `tool_choice: "required"`: модель должна вызвать
инструмент вместо обычного текстового ответа. В основных запросах принудительно
используется `thinking: {"type":"disabled"}`, а `reasoning_effort` не передаётся:
DeepSeek не поддерживает обязательный выбор инструмента в thinking-режиме.
Это описано в [справочнике API](https://api-docs.deepseek.com/api/create-chat-completion/).
Настройки `thinking` и `reasoning_effort` из конфигурации применяются к
суммаризации. Параметр `response_format` не передаётся.

`submit_response` завершает ход локально: результат этого вызова не отправляется
обратно модели. Если другие инструменты не нужны, ответ и обновления памяти
получаются за одно обращение к API. Если нужен калькулятор, время или длина
текста, модель сначала вызывает их, получает результаты обычным циклом tools,
затем отдельно вызывает `submit_response`. Поэтому такой пользовательский ход
может включать несколько обращений к API, но сохранение памяти не добавляет
своего запроса.

Аргументы проверяются локально: обязательные поля, непустые строки, статусы,
категории ключей и конфликты операций. Beta strict-mode не включён, поэтому
валидность аргументов не предполагается заранее. Неверный или обрезанный вызов
отклоняется без записи хода в историю и без изменения памяти; usage учитывается.
Обычный текст вместо `submit_response`, несколько финальных вызовов или смешение
финального и обычных инструментов в одном ответе также считаются ошибкой.
Повторных запросов для исправления нет. `max_tokens` ограничивает генерацию,
включая аргументы с планом и facts; для длинных задач увеличьте его или задайте `0`.

Приложение использует только конфигурационный файл. По умолчанию это
`config.json`; путь можно указать явным аргументом:

```bash
go run ./cmd/llm-console --config config.deepseek.json
```

## Статичные профили поведения

Добавляйте профили в `profiles` файла конфигурации. `name` — уникальное имя
без пробелов, `description` — непустое свободное описание стиля, формата
ответов и ограничений. Например:

```json
{
  "active_profile": "concise",
  "profiles": [
    {
      "name": "concise",
      "description": "Отвечай на русском языке кратко: обычно 2–4 предложения или до 5 коротких пунктов. Используй формальный деловой тон, обращайся на «вы», без шуток, эмодзи и разговорных выражений. Сначала дай результат, затем только необходимые пояснения. Не включай код, псевдокод и команды: объясняй решение словами. Не выдумывай факты; явно обозначай неопределённость."
    },
    {
      "name": "mentor",
      "description": "Отвечай на русском языке подробно и последовательно. Используй формальный профессиональный тон, обращайся на «вы», без шуток и эмодзи. Объясняй предпосылки, решение по шагам, причины выбора, ограничения и возможные ошибки. Для технических вопросов включай практические примеры кода или команд в блоках с указанием языка и поясняй их. Для нетехнических вопросов код не добавляй. Не выдумывай факты; при нехватке данных уточняй их."
    },
    {
      "name": "buddy",
      "description": "Отвечай на русском языке кратко: обычно 2–4 предложения или до 5 коротких пунктов. Общайся неформально и дружелюбно, обращайся на «ты», используй простые разговорные формулировки; допустимы лёгкая шутка и один уместный эмодзи. В технических ответах сразу показывай минимальный пример кода или команд в блоке с указанием языка, затем коротко объясняй его. Для нетехнических вопросов код не добавляй. Не выдумывай факты; явно обозначай неопределённость."
    }
  ]
}
```

| Профиль | Объём | Код в технических ответах | Тон |
| --- | --- | --- | --- |
| `concise` | Кратко | Без кода и команд | Формальный, на «вы» |
| `mentor` | Подробно | С кодом и пояснениями | Формальный, на «вы» |
| `buddy` | Кратко | Минимальный пример кода | Неформальный, на «ты» |

Это фрагмент конфигурации: добавьте эти поля к настройкам API.
Изменения описаний загружаются при перезапуске. Модель не редактирует профили.
Отсутствующее или пустое `active_profile` означает работу без профиля;
неизвестное имя, повторяющиеся имена и пустые описания останавливают запуск.

Команды выполняются локально без обращения к API:

```text
/profile
/profile list
/profile show mentor
/profile use mentor
/profile use buddy
/profile off
```

Выбор действует со следующего запроса до завершения приложения. При следующем
запуске снова используется `active_profile` из конфигурации. Активное описание
передаётся отдельной системной инструкцией в каждый основной запрос, включая
запросы после сжатия истории; в суммаризацию оно не включается. Формат профиля
относится к тексту `answer`, служебный вызов `submit_response` сохраняется.

История и оба слоя памяти общие для всех профилей. Переключение не удаляет
предыдущие сообщения и факты; текущий профиль имеет приоритет над прежними
предпочтениями в контексте. `/clear` сохраняет выбранный профиль. Для нового
диалога без прежней переписки используйте `/clear` отдельно.
Статичные профили поведения и долговременные facts `profile.*` — разные
сущности: facts содержат сведения о пользователе, а профили задают поведение
ассистента. Инструкция запрещает копировать описание профиля в память.

## Диагностика ответов API

Проблемные HTTP-ответы API дописываются в `api-responses.jsonl` рядом с
конфигурацией. Успешные ответы не записываются. Логирование действует для
основного диалога, раундов инструментов и суммаризации. Параметр
`api_response_log_path` меняет путь; значение `-` отключает запись.
Файл лога должен отличаться от конфигурации и всех файлов памяти.

Одна строка содержит только время UTC (`time`), HTTP-статус (`http_status`),
категорию проблемы (`error`) и полное тело ответа в строковом поле `body`.
Сохраняются пробелы, невалидный JSON и частично прочитанное тело.
Настройки конфигурации, данные запросов и HTTP-заголовки в лог не попадают.
Если HTTP-ответ не получен, записывать нечего: транспортная ошибка показывается
в консоли без записи в этот лог.

Категории проблем: `http_error`, `invalid_json`, `read_response`,
`invalid_response`, `no_choices`, `empty_answer`, `truncated_answer`,
`incomplete_response`, `unexpected_tool_calls`, `invalid_tool_call`,
`tool_call_limit`, `missing_final_tool`, `invalid_final_tool`,
`invalid_final_arguments`. Последние три означают отсутствие обязательного
`submit_response`, неверный набор вызовов или невалидные аргументы финальной
функции. Исходное тело ответа сохраняется целиком. `finish_reason`, usage,
`tool_calls` и аргументы функций можно посмотреть внутри `body`.

Права файла — `0600`, лог по умолчанию исключён из Git. При другом имени добавьте
его в `.gitignore`. Ошибка записи показывается в stderr и не отменяет ответ;
ошибка открытия лога останавливает запуск.

В основных запросах пустой `content` допустим, если ответ содержит вызов
инструмента. Если `submit_response` и другие вызовы отсутствуют, ход отклоняется
как `missing_final_tool`. Текстовые ответы без инструментов допустимы только
для суммаризации. Для неё пустой ответ даёт `empty_answer` с диагностикой
`finish_reason` и размерами содержимого.

`finish_reason: length` означает обрезанный ответ: проверьте `max_tokens` и usage.
Обрезанные аргументы не выполняются. Ответы с `content_filter`, `aborted` или
`insufficient_system_resource` также отклоняются. Рассуждения не подставляются
вместо финального ответа. Автоматических повторов нет.
Для разбора сбоя найдите запись по времени и посмотрите `body`.

## История диалога

По умолчанию история хранится в `history.json` рядом с конфигурацией.
Другой файл можно указать через `history_path`. При запуске восстанавливаются
контекст и общий расход токенов. Сохранённая переписка сразу выводится в консоль:
вопросы, ответы, вызовы инструментов и их результаты оформляются как в текущем
диалоге. Под каждым ответом показываются те же строки с `>>>`: расход за
этот ответ и общий расход на тот момент, с теми же отступами и цветом.
После переписки появляется приглашение ввода. Показ истории не вызывает API
и не увеличивает расход токенов.

Если файла нет, начинается новый диалог.

После каждого успешного ответа сохраняются вопросы пользователя, сообщения
ассистента, вызовы инструментов (имя, аргументы, ID), результаты инструментов
и статистика токенов каждого ответа с накопленным итогом на тот момент. Поле `reasoning_content`, если модель его
вернула, тоже сохраняется. Системная инструкция работы с памятью добавляется
при каждом основном запросе и в историю не записывается.

Контекст автоматически суммаризируется перед очередным запросом, когда после
предыдущего саммари накопилось 10 пользовательских запросов. Ответы ассистента,
вызовы и результаты инструментов учитываются в содержании саммари, но не
в счётчике запросов. Первое саммари создаётся перед 11-м запросом пользователя. При обновлении модель получает предыдущее саммари и новые
сообщения; после обновления обычный запрос содержит саммари и текущий вопрос.
Между обновлениями к ним добавляются ещё не сжатые сообщения.

Саммари хранится отдельно в поле `summary`: `content` содержит текст,
`message_count` — количество записей массива `messages`, уже вошедших в него
(включая сообщения инструментов). Полная переписка сохраняется и отображается
как прежде; служебный запрос и саммари в неё не добавляются. После перезапуска
саммари и граница сжатия восстанавливаются. `/clear` сбрасывает и саммари.

Суммаризация — отдельный текстовый запрос к той же модели без инструментов
и JSON-режима. Её токены входят в общий расход диалога.
Если суммаризация не удалась, вопрос не отправляется, прежний контекст остаётся
доступным, а следующая попытка повторяет суммаризацию.

## Модель памяти

Слои хранятся в отдельных файлах. Относительные пути считаются от каталога
конфигурации; все три пути должны отличаться. Отсутствующий файл означает пустой
слой. В основном запросе оба настроенных слоя присутствуют всегда; пустой
обозначается `null`. Модель может заполнить рабочую память по подтверждённым данным
текущего запроса и доступной переписки; отсутствующие сведения она должна уточнять.
Все сохранённые слои загружаются при запуске. Удаление файла во время работы
не меняет уже загруженное состояние: используйте `/memory clear working` для
сброса без перезапуска или перезапустите приложение после удаления файла.

| Слой | Что сохраняется и как | Хранилище | Правило включения в промпт |
| --- | --- | --- | --- |
| Краткосрочная память | Успешные ходы диалога и взаимодействия с инструментами; саммари после каждых 10 пользовательских запросов | `history.json` | Саммари и ещё не сжатые сообщения, затем текущий вопрос; до первого саммари — вся переписка |
| Рабочая память | Модель автоматически ведёт задачу, полный план, текущую стадию, статус, ограничения и результаты | `working-memory.json` | Весь снимок текущей задачи отдельным системным JSON-блоком; без задачи передаётся явный `null` |
| Долговременная память | Модель автоматически выделяет подтверждённый профиль (`profile.*`), решения (`decision.*`) и знания (`knowledge.*`) | `long-term-memory.json` | Все сохранённые facts отдельным системным JSON-блоком; пустой слой передаётся как `null` |

Основа долговременной памяти — `facts` из Дня 10: объект «ключ — строковое
значение». Теперь он хранится отдельно от переписки. Модель сама выбирает,
что относится к текущей задаче, а что должно сохраниться надолго. Она получает
текущую память и передаёт ответ вместе с её изменениями аргументами одного
финального вызова `submit_response`:

```json
{
  "answer": "Учту русский язык. Для задачи составлен план; сейчас разбираем требования.",
  "working_memory": {
    "task": "Разработка консольного ассистента",
    "plan": ["Уточнить требования", "Реализовать память", "Проверить сборку"],
    "current_stage": "Уточнить требования",
    "status": "in_progress",
    "facts": {"goal": "Разделить память на три слоя"}
  },
  "long_term_memory": {
    "upsert": {"profile.language": "Русский"},
    "delete": []
  }
}
```

- `answer` — непустой текст для пользователя.
- `working_memory: null` оставляет задачу без изменений. Объект заменяет снимок
  целиком: `task`, полный `plan`, `current_stage`, `status`, `facts` обязательны.
  План сохраняет все шаги, включая уже завершённые; статус — `in_progress`,
  `blocked` или `completed`. Новая задача получает новый план без старых временных
  данных. Завершённая остаётся со статусом `completed` до следующей задачи.
- `long_term_memory: null` оставляет facts без изменений. Объект содержит
  независимые необязательные операции: `upsert` для добавления и замены по ключу,
  `delete` для явно отменённых или опровергнутых фактов. Пропущенный `upsert`
  означает `{}`, пропущенный `delete` — `[]`; явный `null` вместо операции
  недопустим. Неупомянутые ключи сохраняются. Один ключ нельзя одновременно
  добавлять и удалять. Пустой объект `{}` не меняет долговременную память.

Инструкция модели запрещает принимать её предположения и предложения за
подтверждённые сведения, отмечать запланированные действия выполненными и
сохранять секреты. Реальный прогресс определяется по запросу и результатам
инструментов; временные детали идут в рабочую память. Например, сообщение
«Запомни: я предпочитаю русский» может автоматически обновить `profile.language`,
а «Сборка прошла, переходим к документации» — план и текущую стадию.
Выбор содержимого выполняет модель; приложение проверяет формат и применяет
выбранные операции. Это не гарантирует безошибочность смыслового выбора модели.

Обновление памяти не требует отдельных LLM-запросов. При вызове обычных
инструментов сохраняется цикл `tool_calls`: `submit_response` вызывается
после их результатов. Служебный вызов не передаётся исполнителю инструментов,
не выводится отдельным блоком UI и не записывается как незавершённый tool_call:
в историю попадает обычное итоговое сообщение с текстом `answer`. Суммаризация истории остаётся отдельным периодическим запросом;
она не обновляет другие слои. Её клиент получает обычный текст без инструкции формата памяти.

В промпт сначала попадает инструкция формата и обновления памяти, затем
активный статичный профиль (если выбран),
долговременные facts, текущая задача, саммари с новыми сообщениями и текущий
вопрос. Блоки памяти помечены как данные, а не инструкции. Текущий запрос имеет
приоритет, данные текущей задачи имеют приоритет над долговременными.
Статичный профиль имеет приоритет над предпочтениями из памяти и старой
переписки; служебный протокол ответа и правила памяти сохраняются.
Статистика токенов, отметки сохранения памяти и служебные JSON-ответы
в контекст модели не включаются.

Сначала проверяются все аргументы `submit_response`, затем каждый изменяемый слой сохраняется через
временный файл и замену основного. Запись слоёв независима: если один файл
недоступен, другой может обновиться. Не сохранённый слой остаётся в прежнем
состоянии, консоль показывает ошибку вместе с текстом ответа; сам ответ остаётся
в диалоге. Автоматического повторного запроса или повторного применения patch нет.

Ручные команды остаются для просмотра и исправлений без обращения к API:

```text
/memory show
/memory task Разработка консольного ассистента
/memory set working goal Разделить память на три слоя
/memory set long profile.language Русский
/memory forget long profile.language
/memory clear working
/memory clear long
```

`/memory task` начинает новую задачу с начальным планом из одного шага и
очищает прежние рабочие данные. `/memory set` заменяет значение по ключу,
`/memory forget` удаляет запись. `/memory clear working` очищает задачу целиком,
`/memory clear long` — все долговременные facts. `/clear` удаляет только диалог,
саммари и статистику токенов. При следующем вопросе модель снова может обновить
память по текущей задаче и запросу.

Удаление факта из слоя не стирает упоминания в диалоге и саммари. Чтобы убрать
их из краткосрочного контекста, используйте `/clear`. Для полного сброса нужны
`/clear`, `/memory clear working`, `/memory clear long`.

Рабочий файл содержит поля снимка `task`, `plan`, `current_stage`, `status`,
`facts`; долговременный — объект `facts`. Форматы файлов не версионируются:
поля `version` и проверки номера версии отсутствуют. Приложение работает только
с текущей структурой данных, без миграций и поддержки старых форматов.
История всегда использует саммари с новыми сообщениями.

Запись выполняется через временный файл с последующей заменой основного.
При ошибке сохранения ответ всё равно показывается, контекст остаётся в памяти,
а консоль сообщает, что история не сохранена. Если API вернул ошибку, ход не
добавляется в переписку, но уже полученная статистика токенов сохраняется.

Команда `/clear` удаляет файл истории и сбрасывает контекст и счётчик токенов.
После неё можно сразу продолжить общение с чистого диалога.
Если удалить файл не удалось, контекст и счётчик остаются без изменений.
Уже выведенные сообщения остаются в прокрутке терминала.

Повреждённый JSON или некорректные данные истории останавливают запуск:
существующий файл автоматически не перезаписывается. Для нового диалога
переместите повреждённый файл или выберите другой `history_path`.

Формат файла:

```json
{
  "messages": [
    {"role": "user", "content": "Привет"},
    {
      "role": "assistant",
      "content": "Здравствуйте!",
      "usage": {"prompt_tokens": 10, "completion_tokens": 5, "total_tokens": 15},
      "total_usage": {"prompt_tokens": 10, "completion_tokens": 5, "total_tokens": 15}
    }
  ],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 5,
    "total_tokens": 15
  }
}
```

В итоговом сообщении ассистента `usage` — расход за весь шаг, включая обращения
с инструментами; `total_usage` — общий расход на момент этого ответа.
Статистика не отправляется модели: перед запросом извлекаются только поля
сообщения для API. Верхнеуровневый `usage` хранит текущий общий расход,
включая полученную статистику неуспешных шагов.

`history.json`, `working-memory.json`, `long-term-memory.json` и временные
файлы исключены из Git. При выборе других имён добавьте их в `.gitignore`.

## Архитектура

`cmd/llm-console/main.go` собирает зависимости и запускает чат, `args.go`
разбирает параметры запуска, `console.go` обрабатывает ввод и оформление.
Сценарий диалога и контекст в памяти находятся в
`internal/app/ChatService`; его можно вызвать из desktop-интерфейса без
копирования логики. Контракт `llm.Client` отделяет сервис от API-провайдера.
Пакет `internal/history` отвечает за JSON-историю, `internal/memory` — за
раздельное хранение рабочей и долговременной памяти. `internal/app/memory.go`
задаёт команды записи и правила включения слоёв в промпт.
`internal/app/response_tool.go` задаёт JSON Schema служебной функции
`submit_response`, `internal/app/memory_client.go` — инструкцию автоматического
обновления памяти и проверку аргументов. Адаптер возвращает обычный текст
и типизированные изменения в `llm.Result`; `ChatService` применяет их.
`ChatService` управляет перепиской и общим расходом токенов через контракт
`HistoryStore`; консоль отвечает только за ввод и отображение.

После каждого ответа показывается расход токенов за текущий шаг и за весь
диалог: общее число, входные и выходные токены. Счётчик сохраняется
вместе с перепиской и сбрасывается командой `/clear`. Учитываются все обращения к API, включая
повторную отправку контекста после вызовов инструментов. Если шаг завершился
ошибкой, уже полученная статистика также учитывается.
Суммы строятся по данным `usage` от API: обращения, для которых статистика
не пришла, в сумму не входят. Если данных совсем нет, выводится
«данные недоступны».

## Инструменты модели

В основной запрос передаются четыре функции в формате OpenAI-compatible
`tools`. Три обычных инструмента модель использует по необходимости:

- `current_time` — текущие дата и время в UTC, без аргументов;
- `calculate` — арифметика: `operation` (`add`, `subtract`, `multiply`,
  `divide`) и два числа `a`, `b`;
- `text_length` — количество кодовых точек Unicode в строке `text`.

Четвёртая функция — `submit_response`: обязательный финальный ответ с
обновлениями памяти. Её обрабатывает сервис диалога без дополнительного
обращения к модели.

При вызове обычного инструмента его имя и аргументы выводятся отдельным блоком
до выполнения. Результат (включая ошибку инструмента) показывается следующим блоком.
Сообщения чата и события инструментов выводятся в stdout. Ошибки запуска
выводятся в stderr; ошибки запросов показываются в чате, после них можно
продолжить диалог. Неуспешный ход не добавляется в контекст.

Для обычных инструментов приложение проверяет аргументы, выполняет вызовы
и отправляет результаты обратно модели. Ошибки инструментов также передаются модели. Поддерживается
несколько вызовов за ответ; для одного пользовательского запроса ограничение —
10 обращений к API. Расход токенов суммируется по полученным ответам API.
Поддержка вызова инструментов зависит от выбранного провайдера и модели.
Например, после запуска задайте в чате вопрос: «Сколько будет 123 умножить на 456?»
